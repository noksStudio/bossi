# 04 — ארכיטקטורה ודרכי פיתוח

## עקרונות מנחים

1. **מונוליט מודולרי, לא מיקרו-שירותים.** צוות קטן + דומיין שעדיין זז = מיקרו-שירותים הם
   התאבדות. מודולים עם גבולות ברורים בתוך תהליך אחד; אם מודול יצטרך להיפרד — הגבול כבר קיים.
2. **Postgres הוא מקור האמת היחיד.** גם מסמכים (מטא-דאטה), גם חיפוש (FTS + pgvector),
   גם תור (pg-boss). להוסיף Elasticsearch/Pinecone/Kafka רק כשיש כאב מדוד. הם לא צוואר הבקבוק שלך.
3. **בידוד דיירים באכיפת DB, לא בקוד.** RLS מהיום הראשון.
4. **ה-AI מציע, הקוד מחליט.** מודל שפה אף פעם לא כותב ישירות לטבלת כסף.
5. **הכל אסינכרוני שאפשר.** OCR, embedding, סבבי גבייה, התראות — כולם jobs.

## הסטאק המומלץ

| שכבה | בחירה | למה |
|---|---|---|
| Monorepo | pnpm + Turborepo | אפליקציה + פורטל + workers חולקים טיפוסים וסכמה |
| Web | Next.js (App Router) + TypeScript | אפליקציה ופורטל בקוד אחד, שני layouts |
| UI | Tailwind + Radix / shadcn | **RTL-first** — properties לוגיים, `dir="rtl"`, בדיקה דו-כיוונית |
| API | tRPC או Hono + zod | טיפוסים מקצה לקצה; zod כשכבת ולידציה יחידה |
| DB | Postgres 16 + pgvector + pg_trgm | מקור אמת + חיפוש באותו מקום |
| ORM | Drizzle | קרוב ל-SQL, מיגרציות שקופות, לא מסתיר RLS |
| Jobs | pg-boss (או BullMQ+Redis בהמשך) | להימנע מתלות נוספת עד שיש סיבה |
| קבצים | S3 / Cloudflare R2 | מוצפן, גישה רק ב-signed URL קצר-מועד |
| Auth | Lucia / Auth.js, שני realms נפרדים | staff ו-portal לא מתערבבים לעולם |
| AI | Claude (סיווג, חילוץ, סוכן חיפוש) | tool-use + JSON schema, prompt caching |
| Embeddings | ספק עם עברית טובה — **לבדוק אמפירית** | איכות בעברית משתנה מאוד בין ספקים |
| הודעות | WhatsApp Business API + מייל טרנזקציוני | וואטסאפ הוא הערוץ בישראל |

## מבנה הריפו

```
bossi/
├─ apps/
│  ├─ web/          # אפליקציית העסק
│  ├─ portal/       # פורטל הלקוחות (אפשר route group בתוך web)
│  └─ worker/       # קליטה, OCR, embeddings, התראות, גבייה
├─ packages/
│  ├─ db/           # סכמה, מיגרציות, RLS, seed
│  ├─ core/         # לוגיקה עסקית טהורה — ריטיינרים, גבייה, מחירונים
│  ├─ events/       # taxonomy, publisher, consumers
│  ├─ ai/           # סיווג, חילוץ, חיפוש — עם evals
│  ├─ integrations/ # מורנינג/חשבשבת, סליקה, WhatsApp, אחסון
│  └─ ui/           # design system RTL
└─ docs/
```

**כלל זהב: `packages/core` לא יודע מה זה HTTP, מה זה Postgres ומה זה LLM.**
חישוב שחיקת ריטיינר, תעדוף גבייה ומחיר ללקוח הם פונקציות טהורות עם בדיקות יחידה.
זו הליבה שאסור שתישבר, וזה גם מה שיאפשר לשנות טכנולוגיה בלי לשכתב לוגיקה.

## שכבת ה-AI — איפה, ואיפה לא

### שימושים נכונים
| משימה | דפוס |
|---|---|
| סיווג מסמך | פלט מובנה + ציון ביטחון + סף → תור אנושי |
| חילוץ שדות | JSON schema קשיח, כל שדה עם עוגן במסמך |
| סוכן חיפוש | פירוק שאילתה לפילטרים + חיפוש סמנטי, החזרה עם ציטוטים |
| ניסוח תזכורת גבייה | טיוטה בטון נבחר — **הבעלים מאשר בקליק, לפחות בהתחלה** |
| סיכום ציר זמן | "מה קרה עם הלקוח הזה ברבעון" |

### שימושים אסורים
- לא מחשב סכומים, יתרות ריטיינר, מלאי או ריביות. **חישוב כספי הוא קוד דטרמיניסטי.**
- לא כותב ל-DB ישירות. מציע `proposal` → שכבת אימות → כתיבה.
- לא שולח הודעה ללקוח קצה בלי אישור, עד שיש אמון מוכח.

### Evals מהיום הראשון
`packages/ai/evals` עם סט מסמכים אמיתיים (מעורפלים) ותוצאות צפויות. כל שינוי פרומפט
או מודל רץ מולם. בלי זה כל "שיפור" הוא הימור. מדדים: דיוק סיווג, F1 לחילוץ שדות,
recall@5 לחיפוש.

## אבטחה — תנאי סף, לא פיצ'ר

אתה מחזיק חוזים, חשבוניות ונתוני לקוחות של עסקים אחרים. מכירה לעו"ד או רו"ח לא תקרה
בלי תשובות ברורות.

- **RLS על כל טבלה**, `set local app.tenant_id` בכל טרנזקציה
- **שני realms של זהות** — טוקן פורטל לא מגיע לשום endpoint פנימי (audience נפרד + middleware נפרד)
- קבצים: הצפנה ב-rest, signed URLs קצרים בלבד, אף פעם לא bucket ציבורי
- **Audit log של צפייה במסמכים** — מי, מה, מתי. נגזר מה-events בחינם
- מחיקה: soft delete + retention מוגדר, כולל ייצוא מלא של הדאטה בבקשת הלקוח (GDPR-like)
- הפרדת סודות, אין מפתחות בקוד, 2FA לתפקידי owner

## אינטגרציות — הסדר קובע

**כלל: אינטגרציה אחת בכל שלב. לא שתיים.** כל אינטגרציה היא פרויקט עם edge cases,
webhooks, שגיאות ותחזוקה נצחית.

| עדיפות | תחום | מועמדים | הערה |
|---|---|---|---|
| 1 | הנפקת מסמכים/חשבוניות | Morning (חשבונית ירוקה), iCount, Rivhit | **לא לבנות בעצמך** — חוק החשבוניות והקצאת מספרים מרשות המסים הם עולם רגולטורי שלם |
| 2 | סליקה ולינקי תשלום | Tranzila, Cardcom, PayPlus, משולם | כולל טוקניזציה לחיוב חוזר של ריטיינרים |
| 3 | WhatsApp | 360dialog / Twilio / ספק ישראלי | תבניות מאושרות, חלון 24 שעות, תמחור לשיחה |
| 4 | מייל נכנס | Postmark / Mailgun inbound | הבסיס לצינור הקליטה |
| 5 | קלנדר | Google Calendar | קליטת צריכת ריטיינר בלי חיכוך |
| 6 | ERP / מלאי | חשבשבת, Priority, Rivhit | רק בשלב הפורטל, ואחד בלבד |

## תפעול

- **סביבות:** dev / staging / prod. Staging עם דאטה מסונתזת, לא עותק פרודקשן.
- **מיגרציות:** קדימה בלבד, נבדקות ב-CI על עותק סכמה.
- **גיבוי:** PITR ל-Postgres + versioning על ה-bucket. **ובדיקת שחזור רבעונית** —
  גיבוי שלא נבדק הוא לא גיבוי.
- **תצפית:** לוגים מובנים עם `tenant_id` בכל שורה, Sentry, ומטריקות עסקיות
  (זמן קליטת מסמך, אחוז סיווג אוטומטי, DSO ממוצע) — לא רק מטריקות טכניות.
- **CI:** typecheck, lint, unit על `core`, evals על `ai`, migration check.

## סדר בנייה טכני מומלץ

1. `packages/db` — סכמה + RLS + seed. **RLS לפני הפיצ'ר הראשון.**
2. `packages/events` — publisher + טבלה + taxonomy.
3. Auth (staff בלבד) + מסך לקוח עם ציר זמן ריק.
4. צינור קליטת מסמכים — העלאה ידנית בלבד, בלי AI. תיוק ידני. חיפוש FTS.
5. מייל נכנס → אותו צינור. **כאן המערכת מתחילה לחסוך זמן אמיתי.**
6. סיווג + חילוץ + תור אישור.
7. ריטיינרים + ספר צריכה + תחזית שחיקה.
8. AR + אינטגרציית הנפקה + סולם דחיפה + לינק תשלום.
9. חיפוש סמנטי + ציטוטים.
10. מנוע התראות + דייג'סט WhatsApp.
11. פורטל: קטלוג → מחירון ללקוח → עגלה → הזמנה → סנכרון מלאי.

הסדר לא שרירותי: **כל שלב עומד בפני עצמו ומספק ערך גם אם עוצרים אחריו.**
