# 07 — פלטפורמת המודולים

> מימוש: [`packages/kernel`](../packages/kernel) · מניפסטים: [`packages/modules`](../packages/modules)
> החלטה: [ADR-003](06-decisions.md#adr-003--ארכיטקטורת-מודולים-מתחברים)

Bossi אינה מוצר אחד עם פיצ'רים כבויים. היא **קרנל דק + מודולים שמתחברים**, וכל לקוח
מקבל הרכבה משלו. עורך דין מקבל מסמכים+ריטיינרים+גבייה; מפיץ מקבל מסמכים+קטלוג+מלאי+
הזמנות+פורטל+גבייה. אותו קוד, אותה פריסה, הרכבה אחרת.

## הקרנל מול המודולים

**הקרנל** (תמיד פעיל, אינו מודול): דיירים ו-RLS, שני עולמות הזהות, לקוחות ואנשי קשר,
זרם האירועים, אחסון קבצים, תור העבודות, מסירת הודעות, מרשם המודולים והרשאות.

**מודול** הוא כל דבר אחר. כרגע עשרה:

| מודול | תלוי ב | תיאור |
|---|---|---|
| `documents` | — | קליטה, סיווג, תיוק, תוקף |
| `search` | *(רך: documents)* | חיפוש היברידי עם ציטוטים |
| `billing` | — | חשבוניות, תקבולים, יתרות |
| `collections` | `billing` | תעדוף, סולם דחיפה, הבטחות תשלום |
| `retainers` | `billing` | תקופות, צריכה, שחיקה, חידושים |
| `catalog` | — | מוצרים ומחירונים פר-לקוח |
| `inventory` | `catalog` | מלאי זמין והקצאה |
| `orders` | `catalog`, `billing` | עגלה, הזמנה, אשראי |
| `portal` | — | ממשק צד-לקוח |
| `alerts` | — | מנוע חוקים ודייג'סט |

## שתי דרכי התקשורת — ואין שלישית

**מודול לעולם לא מייבא מודול אחר.** זה הכלל היחיד שמחזיק את כל השאר.

### 1. פורטים — סינכרוני, מטופס

מודול מכריז שהוא *צורך* יכולת. הוא לא יודע מי מספק אותה.

```ts
export const ReceivablesPort = definePort<Receivables>('billing.receivables');

// collections צורך — בלי לדעת ש-billing קיים
consumes: [ReceivablesPort]
// billing מספק
provides: [{ port: ReceivablesPort, factory: () => new PgReceivables(db) }]
```

הקרנל אוכף: ספק **אחד בלבד** לכל פורט, וצריכה מחייבת תלות קשיחה מוצהרת
(אחרת מתקבל צימוד סמוי שנשבר ברגע שמכבים מודול).

### 2. אירועים — אסינכרוני, מנותק

מודול פולט עובדה בלי לדעת מי מקשיב:

```
retainers.period_closed  →  billing מנפיק חשבונית
                         →  alerts שוקל התראה
```

הקרנל אוכף **מרחב שמות**: מודול רשאי לפלוט רק `<module_id>.*`.
בלי הכלל הזה מודול אחד יכול לזייף אירועים בשם אחר, וההרכבה מפסיקה להיות צפויה.

## תרומות UI מותנות — הפיצ'ר שהופך מודולריות לוורסטיליות

הקרנל מגדיר **slots** (`customer.tabs`, `dashboard.widgets`, `customer.actions`…),
ומודולים נתלים עליהם. תרומה יכולה להיות **מותנית בנוכחות מודול אחר**:

```ts
{
  slot: 'customer.actions',
  id: 'collections.reminder_with_evidence',
  label: 'תזכורת + צירוף ראיות',
  requires: ['documents'],   // ← מופיע רק אם גם המסמכים דלוקים
}
```

זה מה שמאפשר ל"גבייה עם ראיות" להתקיים בלי ש-`collections` יכיר את `documents`.
אותו דפוס עובד למטפלי אירועים: `orders.allocate_stock` נדלק רק אם `inventory` פעיל,
ואחרת ההזמנה פשוט נרשמת בלי הקצאה.

**בלי זה, דף הלקוח היה הופך לקומפוננטה אחת ענקית מלאה ב-`if (hasRetainers)`.**
זה בדיוק מה שהורג מערכות מודולריות.

## מה הקרנל אוכף ב-CI

`registry.validate()` רץ כבדיקה ונכשל על:

- תלות במודול לא מוכר · מעגל תלויות
- שני מודולים שמספקים את אותו פורט
- צריכת פורט בלי תלות קשיחה — **הכלל שמונע צימוד סמוי**
- פליטת אירוע במרחב שם של מודול אחר · סוג אירוע בלי מרחב שם
- שתי בעלויות על אותה טבלה

ומתריע (בלי לפסול) על מטפל שמאזין לאירוע שאיש לא פולט.

## הרכבה לדייר

```ts
const registry = createRegistry();
const composition = registry.resolveTenant(['collections']);
// composition.enabled   → ['billing', 'collections']   (תלות לפני התלוי בה)
// composition.autoAdded → ['billing']
```

תלויות חסרות מתווספות **ומדווחות** — לא בשקט. ההרכבה מחזירה: סדר אתחול, מפת פורטים,
ניווט לשני העולמות, תרומות slots ממוינות, טבלת ניתוב אירועים, הרשאות אפקטיביות
ורשימת הטבלאות.

לראות מה מקבל דייר:

```bash
pnpm modules services      # חבילת עסקי שירותים
pnpm modules commerce      # חבילת B2B
pnpm modules documents billing   # הרכבה ידנית
```

## חבילות (`PRESETS`)

`business_type` של דייר הוא **בסך הכול חבילת מודולים מוגדרת מראש**:
`documents` · `services` · `commerce` · `full`.
לקוח מתחיל בחבילה ומוסיף או מוריד מודול בודד מעליה. זה מבטל את הפיצול
בין שני קהלי היעד מ-[ADR-001](06-decisions.md): אין שני מוצרים, יש שתי הרכבות.

## מודול חדש — צ'קליסט

1. הגדר `ModuleManifest` ב-`packages/modules/src/manifests.ts`
2. אירועים במרחב השם שלך בלבד · תלויות ב-`requires` (קשיח) או `enhances` (רך)
3. יכולת שמודולים אחרים יצטרכו → פורט חדש ב-`ports.ts`
4. יכולת שאתה צריך → `consumes` **וגם** `requires` על הספק
5. הצטרפות ל-UI → `slots`, לא עריכת מסך קיים
6. טבלאות בבעלותך בלבד, בקידומת המודול
7. `pnpm check` חייב לעבור

## מה במפורש לא נבנה

**אין טעינה דינמית, אין sandboxing, אין גרסאות ל-API של מודול, אין marketplace.**
כל המודולים מיובאים סטטית ונפרסים יחד. זו החלטה מודעת: הערך הוא בהרכבה פר-דייר,
לא בהרחבה בזמן ריצה. הקרנל כולו הוא 602 שורות (451 ללא הערות), בתקרה מוצהרת של 800 —
אם הוא יגדל מעבר לזה, זה סימן שבנינו framework במקום מוצר.

מודול פרטי ללקוח בודד אפשרי כשיידרש: מניפסט שנרשם רק לדייר מסוים. אין צורך
בשינוי ארכיטקטוני, ולכן אין סיבה לבנות את זה עכשיו.

## כיבוי מודול

`enabled = false` מסתיר ניווט ו-slots ועוצר jobs והאזנות. **הנתונים נשארים.**
מודול שכובה ונדלק שוב חוזר עם ההיסטוריה שלו. אין מחיקה בכיבוי.
